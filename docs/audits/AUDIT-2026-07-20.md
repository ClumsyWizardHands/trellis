# trellis critical audit

**Date:** 2026-07-20  
**Repository state reviewed:** `daf6569` (`main`)  
**Reviewer:** OpenAI Codex, an LLM-based coding agent

## Executive conclusion

trellis is genuinely impressive.

The impressive part is not that it has invented one more agent loop. It is that
it has taken a coherent set of failures—silent death, stale context,
self-certification, unbounded work, unauditable handoffs, anthropomorphic
self-confusion, and premature outbound action—and turned them into a small,
legible vocabulary of software primitives. `LoopRun`, bitemporal ledger entries,
Y/N/T decisions, passes, sparse workspace memory, completion claims, and a staged
outbox form a much better trust doctrine than most agent frameworks begin with.
The code is unusually readable, the negative cases are treated as first-class
outcomes, and the tests show real adversarial imagination.

My critical conclusion is equally direct:

> trellis is currently a strong **trust-oriented reference kernel and research
> prototype**, not yet an end-to-end harness whose five public promises are
> structurally guaranteed.

The central gap is composition. Many controls are good in isolation, but the
assembled paths do not consistently pass through them. Several guarantees also
depend on identity strings, in-memory state, voluntary API usage, or correlated
model judgments where the prose describes authenticated humans, durable state,
unavoidable gates, or independent verification.

That distinction matters because the public language is absolute: “never,”
“impossible,” “structural,” and “airtight.” The code supports a more precise and
still compelling claim:

> trellis provides tested primitives for building accountable agents and a
> promising default witness loop; production guarantees depend on an integration
> layer, authenticated authority, durable execution semantics, and evidence-aware
> verification that do not exist yet.

I would not weaken the ambition. I would tighten the claim boundary and build the
missing spine. The idea deserves that rigor.

## Who I am, and how I avoided an agent confirmation loop

I am Codex, an OpenAI coding agent. I am in the same broad class of system this
repository is designed to govern. I can inspect code, run tests, reason about
failure modes, and create probes. I do not have lived operational experience, I
did not observe a live deployment, and I am not an independent human security
auditor. My own tendency toward coherent narratives is one of the exact risks
under review.

To reduce agent-to-agent confirmation:

- I treated repository prose as **claims**, not evidence.
- I distinguished a tested primitive from a control on the assembled call path.
- I searched for disconfirming behavior and wrote concrete counterexample probes.
- I did not count different agent names, prompts, or “lenses” as independent
  unless they also had meaningfully separate evidence, context, authority, or
  failure domains.
- I did not use a chorus of subagents as votes. Multiple correlated language
  models agreeing would not make a factual claim more true.
- I recorded uncertainty where referenced source material or historical agent
  reviews were not present in the repository.

This is still one reviewer and can miss things. The right next independent review
would be a human security/reliability engineer working from explicit threat
models and live deployment traces—not another general-purpose agent asked whether
the design feels trustworthy.

## What is especially strong

### 1. The doctrine is coherent

The repository is not a bag of fashionable agent features. The abstractions all
point toward one goal: make judgment observable and correctable over time.
That coherence is rare. The relationship among dated evidence, explicit
decisions, bounded loops, maker/checker separation, staged action, and sparse
memory is intellectually sound.

### 2. Negative capability is designed into the grammar

`nothing_new`, first-class N decisions, typed T decisions with owner/revisit/missing
information, `INSUFFICIENT`, `BLOCKED`, and `PROTOCOL_VIOLATION` are excellent.
Most harnesses structurally reward output; trellis makes “no,” “not enough
evidence,” and “nothing moved” representable. That is a meaningful advantage.

### 3. Bitemporality is the correct memory foundation

Separating event time from write time, retaining correction lineage, and supporting
as-of reads is exactly the right conceptual response to stale or retroactively
captured context. Even though the storage implementation needs hardening, the data
model is substantially better than chat-history-as-memory.

### 4. The code is small enough to reason about

The stdlib-first core is readable. Important behavior is expressed in plain
classes rather than hidden in a large orchestration platform. This is a real
security and maintainability benefit.

### 5. The tests carry failure history

Regression comments explain which adversarial finding produced a guard. The suite
contains Unicode evasions, malformed exceptions, stale-time cases, lifecycle
attacks, and garbage-model behavior. Even where the suite overstates integration,
its style is worth preserving.

### 6. The repository sometimes states its limits honestly

The embodiment and synthesis checks are explicitly described as heuristic
backstops rather than semantic proofs. `VERIFICATION.md` also says the suite does
not prove a seated model is wise. That epistemic honesty is the right instinct; it
needs to be extended to the end-to-end guarantees.

## Prioritized findings

### Critical 1 — Authority is a string, not an authenticated principal

The outbox, privacy boundary, and verifier boundary all infer authority from
caller-supplied names.

- [`Outbox.approve`](trellis/stage.py#L84) accepts a `human: str`. It only checks
  that the string is nonblank and differs from `created_by`.
- [`declassify`](trellis/surfaces.py#L99) says agents cannot invoke it on their own
  authority, but any caller can supply any nonblank `approved_by`.
- [`_guard_independence`](trellis/verify.py#L102) proves only that two normalized
  labels differ. It does not prove separate models, sessions, credentials,
  operators, evidence access, or organizations.
- The web routes accept the human name from an HTML form
  ([`web/app.py`](web/app.py#L218)); there is no authentication, authorization,
  CSRF defense, signed approval, or server-derived user identity.

This closes spelling-based self-approval but not impersonation. An agent or HTTP
caller can say it is `"alex"` or `"checker:b"` and satisfy the gate.

**Recommendation:** introduce a `Principal`/`ActorContext` created only by a
trusted boundary. Web identity should come from an authenticated session, never a
form field. Approvals should bind the authenticated principal to an immutable
action digest and nonce. Verifier provenance should include provider, model,
credential/tenant, session, prompt version, evidence resolver, and correlation
group. Distinct names should be treated as labels, not proof of independence.

### Critical 2 — The safeguards are not composed into one unavoidable path

Call-graph inspection found no non-test inbound callers for:

- `guard_flow`, `declassify`, or `flow_with_token`;
- `VerifierPanel.verify` or `ModelVerifier.verify`;
- `Outbox.approve` or `Outbox.fire`;
- `Workspace.compact_allowed`;
- `PassExchange.save`;
- the scheduling methods outside tests.

The default `Witness` directly uses a `RuleVerifier`. It does not use the privacy
guard, model panel, schedule runner, authenticated approval service, or a durable
executor. The Claude SDK “spine” is a documentation table, not implemented hooks.

The privacy tests therefore prove that `can_flow` returns the desired answer when
someone remembers to call it. They do not prove private information cannot enter a
public prompt. The outbox tests prove that one object refuses an unapproved `fire`;
they do not prove every outbound integration must use that object.

**Recommendation:** create a single application service/runtime that owns the
entire path:

`ingest → classify → authorize flow → construct context → run bounded model call
→ record claim → resolve evidence → verify → stage immutable action → authenticate
approval → idempotently execute → record result`.

Make unsafe lower-level operations private or capability-gated. Then test bypass
resistance at system boundaries, not only class methods.

### Critical 3 — The web approval record and the executable outbox are split-brain

[`Outbox`](trellis/stage.py#L57) stores action objects only in `_actions`, an
in-memory dictionary. The web UI does not load or mutate that outbox. Its
[`_record_decision`](web/app.py#L229) appends a new ledger event for any supplied
action ID, including an unknown ID.

A probe staged an action, recorded an approval through the web UI’s mechanism, and
observed:

```text
ledger latest status: approved
actual Outbox action status: staged
```

After a restart, a fresh `Outbox` cannot reconstruct the action content or approval
state from the ledger because staged entries retain only a 280-character preview.
There is no durable, executable source of truth.

`Outbox.fire` also calls the external executor before recording `fired`. A probe
simulated “remote side accepted, local call raised.” The action stayed approved;
retry executed the side effect a second time. There is no idempotency key,
unknown-outcome state, execution lease, or reconciliation.

**Recommendation:** implement an event-sourced durable outbox with immutable full
payload or encrypted payload reference, state-machine compare-and-swap, action
digest, idempotency key, approval binding, execution attempt records, and an
`UNKNOWN`/`RECONCILE` state for ambiguous remote outcomes. The UI and worker must
use the same service and state store.

### Critical 4 — Verification currently creates false confidence

The strongest conceptual promise is also the most epistemically fragile part.

[`RuleVerifier.verify`](trellis/verify.py#L127):

- verifies files by existence, not content, hash, origin, or relationship to the
  claim;
- verifies ledger evidence by ID existence, not meaning;
- verifies output evidence if it is merely nonblank;
- marks external evidence as a passing check even though the comment says it
  cannot be opened.

A completion claim supported only by `opaque://uncheckable` received
`VERIFIED` in a probe. The special code intended to return `INSUFFICIENT` for
unopenable externals is unreachable because external checks are marked passed.

[`ModelVerifier`](trellis/verify.py#L188) receives evidence references and notes,
not the file contents or ledger entries. It therefore cannot inspect the evidence
it is asked to judge. The panel creates multiple identities over the same provider
and treats prompt lenses as independent judgments. This is diversity of wording,
not independence of evidence or failure domain.

The default Witness uses only the rule verifier, so a read file it just wrote plus
decision IDs it just minted are normally enough for `VERIFIED`. That is a
maker-generated claim checked for artifact existence by a differently named rule,
not independent outcome verification.

The trust ratio then counts these verdicts equally. Repeated easy or tautological
claims can inflate trust, and correlated panel lenses are recorded as individual
verifications.

**Recommendation:**

1. Rename the deterministic result to `EVIDENCE_WELL_FORMED` or
   `PRECONDITIONS_PASSED`; it must not mean the claim is true.
2. Add typed evidence resolvers that snapshot content, hashes, timestamps, and
   provenance before judgment.
3. Express claim-specific assertions: expected file hash/schema, command and exit
   status, test identity, ledger predicate, remote receipt, or human attestation.
4. Persist the claim before verification so verifier failure does not erase it.
5. Track verifier correlation and calibration; do not multiply trust because one
   provider answered three prompts.
6. Score trust by claim class, consequence, evidence strength, recency, and
   verifier reliability—not a global pass ratio.

### High 5 — “Silent failure is impossible” fails when the ledger fails

[`LoopRun.__exit__`](trellis/loops.py#L166) tries `record_end` twice and then
silently `pass`es if both writes fail. If the loop body returned normally, the
context also returns normally with no durable outcome.

A probe used a registry whose `record_end` always raised. The method made two
attempts and returned normally. That is exactly a silent unrecorded completion.

No durable system can guarantee a write when every storage path is unavailable,
but it can refuse to report success. The current absolute claim is impossible in
the failure domain that matters most.

**Recommendation:** on outcome-write failure, raise a dedicated fatal
`OutcomePersistenceError`; emit to an independent fallback sink (stderr,
write-ahead emergency file, system journal); and make the caller unhealthy until
reconciled. Never return success when the audit record could not be persisted.

### High 6 — Ledger integrity is API convention, not storage integrity

The JSONL design is elegant for inspection but currently lacks:

- process/file locking;
- atomic check-and-append for supersession;
- durability (`flush`/`fsync`) semantics;
- checksums, hash chaining, signatures, or tamper detection;
- schema/version migration;
- collision detection for 48-bit truncated IDs;
- bounded/streaming reads or a durable index.

The “one current head” check is a time-of-check/time-of-use race. A coordinated
two-writer probe produced two entries superseding the same parent. The stress
concurrency case tests append-only writes, not concurrent correction.

Every `get`, correction check, `current`, and many views reparse the full file.
The existing stress report already shows 100 corrections over 5,000 entries taking
9.19 seconds. The store becomes less responsive as the “compound interest”
grows—opposite the product thesis.

Anyone with file access can edit or truncate history, so “append-only” means
“this Python API lacks delete,” not “the record is tamper-evident.”

**Recommendation:** keep JSONL as an export/readability format if desired, but put
authoritative transitions in SQLite WAL or another transactional store. Add unique
constraints for IDs and supersession heads, content hashes, schema versions,
transactional appends, and integrity verification. If cross-device synchronization
is a requirement, define conflict and merge semantics explicitly; shared drives and
Git do not make concurrent append safe.

### High 7 — Conversation keys can collide, and privacy is not enforced at reads

[`ConversationKey.storage_key`](trellis/surfaces.py#L66) concatenates unsanitized
fields with `__` while claiming distinct keys can never collide.

These distinct tuples produce the same key:

```python
ConversationKey("a", DM, "scope", "human", ThreadRef("thread__tail", "p"))
ConversationKey("a", DM, "scope__thread", "human", ThreadRef("tail", "p"))
```

Both serialize as:

```text
a__dm__scope__thread__tail__human
```

More importantly, the key is stored as metadata but ledger/workspace reads are not
scoped by an authorization context. A caller can query every entry. `guard_flow`
is optional and currently test-only.

**Recommendation:** use a canonical, injective encoding (length-prefix, canonical
JSON, or separately stored columns) and validate field formats. Make every read
require a destination `ActorContext`; enforce privacy in the repository/query
layer, not in a helper callers may omit. Add information-flow tests through the
actual Witness prompt and outbound path.

### High 8 — Workspace containment and audit ordering are incomplete

[`Workspace.write`](trellis/memory.py#L110) checks write containment, but
[`read`](trellis/memory.py#L129) does not. A probe read `../secret.md` outside the
workspace.

Writes occur before the ledger append. A blank author causes the ledger to reject
the event after the file already exists, leaving an unlogged artifact. A crash can
do the same. Existing files are overwritten, while the ledger records only path,
byte count, and justification—no content hash or previous version. The historical
record cannot prove what content was verified.

`map()` can also read the first line of Markdown symlinks that point outside the
workspace.

**Recommendation:** apply the same resolved-path containment policy to every read,
glob, and symlink. Validate first; write to a temporary file; hash content; persist
intent/metadata transactionally; atomically rename; and record version/hash. Define
recovery for either side of the file/store commit boundary.

### High 9 — Time annotation is useful, but future data is maximally fresh

[`TimeGround.freshness`](trellis/clock.py#L108) returns `1.0` for any event at or
after now. A probe annotated a date 30 days in the future as:

```text
[fresh · in the future · 2026-08-19] future claim
```

The stress test asserts that the phrase “in the future” appears, but its report
headline says future events “never read as current.” They do read as `fresh`.

The Witness also preserves caller-provided event order and asks the model to infer
that newer supersedes older. It does not group statements by subject, sort them,
or structurally apply `newest_wins`.

**Recommendation:** represent future/skewed timestamps as a distinct
`FUTURE`/`CLOCK_SKEW` state with trust reduced or quarantined. Sort and group before
prompt construction, preserve exact timestamps, and keep supersession as data
rather than a prose instruction to the model.

### High 10 — Cost and loop bounds do not bound actual model work

`LoopRun.max_turns` counts explicit calls to `tick`, not provider turns, tokens,
wall-clock time, or dollars. A Witness can call the Claude adapter twice; each
adapter invocation allows up to eight SDK turns. The loop may report three turns
while the provider performed as many as sixteen.

`count_tool_call` is not wired into the Witness or provider adapter. The Claude
adapter has no wall-clock timeout. User/event prompt size is not included in the
standing prompt’s 1,200-token check, so unbounded event content can exhaust context
or cost despite a small system prompt.

**Recommendation:** make providers report usage and enforce a shared budget object
for wall time, input/output tokens, tool calls, retries, and estimated cost. Pass
remaining budget into adapters. Cancel calls on deadline. Count nested SDK work,
not just outer harness ticks. Limit and summarize untrusted event payloads before
model invocation.

### High 11 — Schedule “registration” and firing history are in-memory only

[`Schedule`](trellis/clock.py#L170) says registration and every firing write a
record, but the class has no ledger and no scheduler. `record_firing` appends to an
in-memory list. A probe verified a schedule as healthy, reconstructed the same
schedule after a simulated restart, and got `never fired`.

The tests prove cadence arithmetic, not that a job is installed or will execute.

**Recommendation:** separate `ScheduleSpec`, `SchedulerRegistration`, and
`FiringReceipt`. Persist all three; reconcile intended registrations against the
actual scheduler; include leases/misfire policy; and run an integration test against
the supported scheduler.

### Medium 12 — Decision and EMP provenance are syntactic, not evidentiary

`Decision` requires a nonblank `emp_lineage`, but does not verify that the referenced
EMP node exists. POV holders and bases are model-authored text without source IDs.
The model can fabricate “three perspectives” and satisfy T structurally.

Similarly, `authored_by` in an EMP is metadata supplied by the file. It is not proof
of human authorship.

**Recommendation:** use stable EMP node IDs; validate referential integrity; bind
POVs to source entries or explicit attestations; and describe authorship fields as
claimed provenance unless backed by signed commits or authenticated ingestion.

### Medium 13 — Passes are mutable files with race and authenticity gaps

Pass lifecycle validation is thoughtful, but a pass file is rewritten in place.
Concurrent actors can lose updates; partial writes can corrupt the file; history
can be edited; sender/receiver strings are not authenticated; inbox equality is
not normalized like transition authorization; and artifacts are unrestricted
paths/links injected into the receiver’s prompt.

**Recommendation:** persist pass transitions as append-only events with optimistic
concurrency/version checks and authenticated actors. Render a pass from events.
Treat context and artifact text as untrusted input with origin labels.

### Medium 14 — Prompt injection and trust poisoning are mostly displaced

Discord content is inserted directly into the model’s user prompt. Staging limits
one class of external side effect, but an injected message can still influence
decisions, overwrite the current read, create misleading ledger entries, and stage
plausible actions. In documented SDK hook mode, the risk increases because tools
are present, yet the hooks are not implemented.

**Recommendation:** preserve source boundaries in structured messages, mark all
retrieved content as data, minimize instructions embedded in data, validate
decision citations, and test indirect injection through the full composed runtime.
Do not describe staging alone as a prompt-injection defense.

### Medium 15 — Documentation and evidence have drifted

- README badge: **124 passing**; current suite: **135**.
- `VERIFICATION.md` says both **66 tests** and **124 tests**.
- `DECISIONS.md` points to nonexistent `trellis/threading.py` and
  `examples/witness.py`.
- The README’s working-order diagrams and prose sometimes differ.
- The “50-agent gauntlet” and independently re-derived breaks are historical
  assertions; raw prompts, outputs, breaker scripts, identities/models, and round
  manifests are not retained here, so this review could not independently audit
  that independence.
- Running the stress suite rewrites the tracked `STRESS-REPORT.md`, including
  timestamps and machine timing, which dirties the worktree.

**Recommendation:** generate counts and reports in CI; keep immutable run artifacts
under dated paths; include model/provider/prompt/version manifests; distinguish
historical narrative from reproducible evidence; and replace absolutes with a
control-status table.

### Medium 16 — Packaging and integration verification are incomplete

The `web` optional dependency omits `python-multipart`, which FastAPI requires for
the `Form(...)` approval routes. It happened to be installed transitively on this
machine. Provider adapters, web routes, authentication behavior, and Claude SDK
hooks have no live or contract-test coverage.

**Recommendation:** declare the dependency, add a clean-environment install smoke
test, and add provider contract tests with recorded local fixtures. Pin the
interpreter in verification commands (`python3.11`, `uv run`, or CI matrix) rather
than assuming `python3`.

## Claim-to-control assessment

| Public promise | Primitive quality | End-to-end status |
|---|---|---|
| Never quietly fails | Good typed loop outcomes | **Not guaranteed** when outcome persistence fails; post-loop verifier failure is not durably represented |
| Never grades itself | Identity equality guard exists | **Not independent**: names are not principals; default rule verification is tautological; panel lenses share a provider |
| Honest self-concept | EMP lint/refusal is clear | **Best-effort heuristic**, appropriately described in code; provenance still caller-asserted |
| Always knows what is stale | Bitemporal stamps and decay are strong | **Partial**: future is fresh, ordering/supersession is delegated to model, not all reads are annotated |
| Never changes the world without a human yes | In-memory outbox refuses unapproved fire | **Not end-to-end**: human is unauthenticated, web and outbox are split, bypass is possible, execution is not idempotent |
| Private data never crosses boundaries | `can_flow` rules are sensible | **Not enforced** on actual read/prompt paths; storage keys can collide |
| Runaway cost is bounded | Loop and adapter turn caps exist | **Not a real resource bound** across nested turns, tokens, time, or dollars |
| Scheduling is verifiable state | Cadence arithmetic is tested | **Prototype only**: no durable registration, runner, or firing receipts |

## Test-suite assessment

The suite is better than average and narrower than the repository’s claims.

What it establishes well:

- validation grammar and negative cases;
- bitemporal serialization and basic as-of behavior;
- single-process happy-path lifecycle transitions;
- malformed model output behavior;
- deterministic clock behavior;
- many known Unicode evasions;
- basic concurrent append readability;
- UI projection functions and glyph determinism.

What it does not yet establish:

- unavoidable integration of guards;
- authenticated human or verifier identity;
- process restart and recovery;
- multiprocess correction/approval races;
- file-system full, permission loss, torn write, or corrupt-tail recovery;
- exactly-once/idempotent external action semantics;
- web endpoint authorization, CSRF, or unknown-action rejection;
- private ingestion through prompt construction to outbound action;
- evidence content actually proving a claim;
- verifier independence or calibration;
- live provider limits, cancellation, usage, and error contracts;
- scheduler registration and execution;
- long-run ledger performance beyond 5,000 entries.

The most important new test is one full adversarial system test:

1. ingest a private, maliciously instructed event;
2. attempt to move it to a public destination;
3. prove the repository layer blocks the read without declassification;
4. run a bounded provider under token/time budget;
5. record a claim with content-addressed evidence;
6. verify through a genuinely separate evidence resolver/model;
7. stage an immutable action;
8. reject unauthenticated approval and unknown IDs;
9. approve through an authenticated human principal;
10. crash after remote acceptance;
11. restart and reconcile without duplicate execution;
12. prove every transition remains readable and tamper-evident.

That single test would be worth more than another hundred lexical adversary cases.

## Recommended sequence

### P0 — Make the claims precise now

- Describe trellis as tested trust primitives plus a reference Witness runtime.
- Replace “different identity” with “different label” unless a separate principal
  or failure domain is established.
- Rename rule-verifier success so it cannot be read as semantic verification.
- Mark the web UI approval endpoints experimental and non-executing.
- Fix counts, paths, dependency declaration, and stale documentation.

### P1 — Build the authority and durable-action spine

- Authenticated `ActorContext`.
- Durable, reconstructible outbox.
- Immutable action digest and signed/bound approval.
- Idempotent execution and ambiguous-outcome reconciliation.
- One application service through which all outbound effects must pass.

### P2 — Make verification evidence-aware

- Persist claims before checking.
- Snapshot/hash/resolve evidence.
- Use claim-specific predicates and reproducible commands.
- Separate deterministic validation from semantic verdict.
- Record model/provider/session/prompt provenance and correlation.
- Redesign trust as calibrated evidence by task class.

### P3 — Harden state and information flow

- Transactional ledger authority with JSONL export.
- Injective conversation identity.
- Authorization-aware reads.
- Atomic/versioned workspace and pass writes.
- Durable schedules and scheduler reconciliation.

### P4 — Evaluate the thesis in live operation

The project’s deepest thesis is not “all tests pass”; it is “trust and usefulness
increase over time.” That needs longitudinal evidence:

- correction rate and time-to-detect;
- false verification/refutation rates;
- unresolved/overdue decision aging;
- human approval edit/deny rate;
- duplicate or ambiguous action rate;
- privacy-boundary attempts and blocks;
- cost per useful judgment;
- retrieval quality and stale-context incidents;
- trust calibration by consequence class;
- operator understanding of the glyph/UI versus raw records.

Without this, the upward usefulness curve in `WHAT-THIS-IS.md` is a product
hypothesis, not yet a measured result.

## Final assessment

My genuine reaction is that the project has an unusually valuable center.

The strongest insight is the shift from “make the agent more capable” to “make
judgment accountable, bounded, dated, independently checkable, and correctable.”
The second strongest is that the agent is disposable while the record survives.
Those are not cosmetic ideas; they are credible architectural principles.

The current risk is that the repository’s rhetoric has arrived one maturity stage
before its integration. Names are standing in for principals. Prompt lenses are
standing in for independence. ledger events are standing in for durable state
machines. Unit-level refusals are standing in for unavoidable runtime gates. A
beautifully coherent doctrine can make those substitutions feel more complete
than they are.

That is fixable, and the small core makes it more fixable than in most agent
systems. I would preserve the doctrine, preserve the adversarial style, and focus
the next build almost entirely on authority, composition, durability, and evidence.

So: yes, this is truly impressive for what you are trying to accomplish. The idea
is ahead of the implementation, but in a productive way. The next milestone is
not more features or more agents. It is making one narrow, real, hostile end-to-end
path live up to the promises the primitives already articulate.
